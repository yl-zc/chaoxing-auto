## 1. 目标与范围

### 1.1 一句话目标

做一个「大模型主导的 **感知 → 规划 → 调度 → 执行 → 验收**」闭环：模型读图识别当前页面有哪些任务、生成结构化任务清单；调度层把每个任务变成**自包含任务书**交给**全新上下文的子 agent** 执行；回执与证据落盘、外部任务板记账；主上下文只保留 **≤2k tokens** 的任务板摘要，从而在长任务（如学习通 28 个章节测验）中不爆上下文、不丢状态。

### 1.2 设计目标

1. **LLM 主导判断**：模型负责「看到什么、要做什么、做完没有」；脚本负责「怎么安全地做」。
2. **可复用引擎**：感知/规划/调度/执行/验收/状态各层与领域解耦，学习通只是**第一个适配实例**。
3. **长任务不爆上下文**：主上下文只维护任务板摘要；每个子任务在**新上下文**中执行并返回结构化回执。
4. **可复核**：每个「已完成」都必须有证据（截图/页面数字/任务点），并可由第三方按 ledger 复算。

### 1.3 范围

| 做 | 不做（默认） |
|---|---|
| 学习通任务点识别（章节/视频/测验/进度） | ❌ 下载/安装模型或新依赖 |
| `tasks.json` 任务清单生成与维护 | ❌ 模型直接点击/导航/提交（由脚本执行） |
| 逐任务派发 fresh 子 agent + 结构化回执 | ❌ 无授权的提交（默认测试模式零提交） |
| 三源对账与完成标记 | ❌ 抢前台/OS 自动点击/碰用户 Chrome |
| 断点续跑、幂等、防重复提交 | ❌ 改接口报文、伪造进度、绕验证码 |
| 汇总报告与准确率统计 | ❌ 直播/阅读/考试（用户既有排除项） |

### 1.4 术语

- **任务（task）**：一条可独立验收的工作单元（如「完成 1.2 章节测验」）。
- **任务板（board）**：`tasks.json`，唯一状态真源。
- **回执（receipt）**：子 agent 返回的固定 schema 结果（**≤500 tokens**）。
- **ledger**：append-only 事件流水（派发/回执/验收/标记/异常），用于断点与审计。
- **fresh 子 agent**：无父会话历史的执行者，只拿任务书 + 白名单工具 + 写范围。

## 2. 核心原则

1. **模型管判断，脚本管动作**：VLM 识别页面/题目；主模型规划任务；点击/导航/回填/提交交给确定性脚本（可审计、可回放、不误触）。
2. **状态外置，不靠上下文记忆**：任何「做到哪、下一步、证据在哪」都写 `tasks.json` / `ledger.jsonl`；上下文丢了可从磁盘恢复。
3. **每个任务一个全新上下文**：子 agent 无历史、任务书自包含（目标/输入/步骤/验收/写范围/停止条件），执行完即回收。
4. **结构化回执，不读长日志**：回执固定 schema、**≤500 tokens**；截图/日志**只给路径**；主模型按回执 + 验收结果更新任务板。
5. **不轻信自述**：子 agent 说「完成」不算；必须三源对账（页面数字/任务点/marker/截图）通过才标 done。
6. **小步、可回滚、可中断**：默认测试模式（只填不交）；提交是唯一不可逆动作，单独闸门、逐节授权。
7. **确定性优先**：同一任务书应产生同一动作序列；随机性只允许来自 VLM 输出，且需置信度与人工抽检兜底。

## 3. 分层架构

### 3.0 数据流

~~~
页面/课程 ──CDP截图──> 感知层(VLM) ──候选任务──> 规划层(主模型) ──tasks.json──> 调度层
                                                                             │ 取 ready 任务
                                                                             ▼
                                                                     自包含任务书 + fresh 子 agent
                                                                             │ 执行（脚本白名单）
                                                                             ▼
                                                                     回执(receipt) + 证据(路径)
                                                                             │
                                                                             ▼
                                                              校验层(三源对账) ──> 状态层(board/ledger)
                                                                             │
                                                                             └── 未通过 → 重排/人工/停止
~~~

### 3.1 感知层（Perception）

- 输入：CDP 截图（整视口）、当前 URL/章节、页面数字；**不读 DOM 题面文本**（学习通题干存在 `font-cxsecret` 混淆，已实测）。
- 处理：本地 VLM（Qwen3-VL-4B + mmproj）识别「页面/章节/任务点/题型/进度/是否已完成」，输出 `perception.json`（候选任务 + 置信度 + 截图路径）。
- 约束：**单实例、串行、常驻加载**（避免每任务重复加载 ≈2.07 s）；只读，不点击。

### 3.2 规划层（Planning）

- 输入：`perception.json` + 人工目标/用户授权范围 + 既有 board。
- 处理：主模型生成/更新 `tasks.json`：拆粒度、定依赖、定完成判据、定风险等级、定是否需人工闸门。
- 约束：任务粒度以「一次可验收」为准（如单节测验 = 1 任务）；提交类任务必须带 `gate` 字段。
- **重规划**：failed/unknown 回规划层 → 修正任务书或拆小任务（attempts+1，上限 1 次），超限转人工；不盲目重试。
- **依赖关系实测前不硬编码**：如「测验是否依赖视频完成」当前未证实，默认按可先行处理，M4 实测后回填 `deps`【待实测】。

### 3.3 调度层（Scheduling）

- 取 ready = `status=pending` 且 deps 全 done、未超重试上限、未命停线。
- 生成**自包含任务书（≤1.5k tokens）**：任务 id/目标/输入（路径/URL/章节）/允许动作/禁止动作/写范围/验收标准/停止条件/回执 schema。
- 派发 fresh 子 agent（DSH `spawn_teammate`/`subagent` 机制；**深度/并发上限待实测**，若受限则退化为串行子任务并强制裁剪上下文）。
- 收回执 → 校验 schema/证据 → 更新 board（running→done/failed/unknown）→ 写 ledger。
- 幂等：任务去重键 = `sec+type`；派发前检查 ledger 是否已有同键 running/done；提交类额外检查「是否已提交」。

### 3.4 执行层（Execution，子 agent）

- 工具白名单：只读查询 + 运行既有脚本 + 写任务专属目录；**禁止**下载/安装/改 docs/改既有代码/碰用户 Chrome/抢前台。
- 写范围：`work/auto-planner/<task-id>/` 与 evidence 路径；不得跨任务写。
- 纪律：异常即停；不重试提交；不伪造证据；回执必须含证据路径与关键数字。
- 生命周期：派发→执行→回执→回收；子会话不共享历史，任务完成即结束。

### 3.5 校验层（Verification）

- **三源对账**：①页面数字（进度 N/59、任务点 `jobUnfinishCount`）②任务点/marker（卡片状态、绿勾）③截图（结果页/课程页）+ 回执关键字段。
- 规则：三源一致且满足完成判据 → done；任一缺失/冲突 → unknown（转人工）；提交类必须额外核对「第 N 次作答/成绩」。
- **校验者与执行者分离**：调度层/独立 auditor 复核，不采信子 agent 自述。

### 3.6 状态层（State）

- `tasks.json`：唯一状态真源（字段见 §5.1）。
- `ledger.jsonl`：append-only，记录 `task_id/ts/event/actor/from/to/receipt_path/evidence_path/error`。
- 断点续跑：启动时读 board+ledger，跳过 done、重排 failed/unknown、running 超时回收为 pending。
- 幂等/防重复提交：提交任务记录 `submit_attempted_at/result/attempt_no`；已提交任务永不再派发。

## 4. 上下文与内存控制（硬约束）

| 对象 | 预算 | 做法 |
|---|---|---|
| 主上下文（Lead/规划者） | 任务板摘要 **≤2k tokens** | 只读 board 摘要（id/sec/type/status/证据路径），不读长日志/截图；按需单任务展开 |
| 子 agent 任务书 | **≤1.5k tokens** | 自包含模板；只给路径不给内容；禁止把整份报告塞进去 |
| 子 agent 回执 | **≤500 tokens** | 固定 schema（status/evidence/key_numbers/errors/next）；长解释落盘 |
| 截图/日志 | **0 tokens（只传路径）** | 落盘 evidence/；主/子上下文只看路径与哈希 |
| VLM 内存 | 常驻 **≈4.04 GB RSS**【实测】 | 单实例、串行、复用一个进程；不按任务重载；n_ctx 4096 |
| Chrome + VLM | 15.62 GB 内共存 | 串行；不开多个 automation 窗口；监控 RSS，>10 GB 停 |
| DSH 子会话 | 每任务隔离、用完回收 | fresh 上下文；任务结束即关闭；不留长历史 |
| 状态文件 | 磁盘 | `tasks.json` + `ledger.jsonl`；主上下文只加载摘要/增量 |

补充：

- 主模型只在「需要判断」时读感知/回执摘要；执行细节由子 agent 处理。
- 子 agent 若需看截图，只读任务目录内文件；**不得把大图 base64 回传给主上下文**。
- 上下文压缩策略：每完成一个任务，主上下文只保留「board 摘要 + 最近 3 条 ledger 摘要」。
- **硬约束的验收方式**【待实测】：M4 用上下文打点实测「主上下文增量 ≤2k tokens、回执 ≤500 tokens」。

## 5. 任务清单与完成标记规范

### 5.1 `tasks.json` 字段（最小）

| 字段 | 说明 |
|---|---|
| id | 稳定唯一（如 `quiz-1.2`、`video-2.1`） |
| type | quiz / video / read / live（后两者默认 excluded） |
| target | sec/chapterId/URL 模板（**不含过期 enc**） |
| criteria | 完成判据（见 §5.4） |
| deps | 前置任务 id 列表 |
| status | pending/running/done/failed/unknown |
| evidence | 证据路径数组（截图/JSON/jsonl） |
| gate | none / human_confirm / submit_authorized |
| attempts | 执行次数/重试上限 |
| notes | 模型/人工备注（简短） |

### 5.2 回执 schema（子 agent → 调度层，≤500 tokens）

~~~
{task_id, status: done|failed|unknown,
 key_numbers: {progress_before, progress_after, task_points_before, task_points_after, attempts, score?},
 evidence: [paths], actions: [short], errors: [short], elapsed_s, submitted: false|true}
~~~

### 5.3 状态机

`pending → running → done / failed / unknown`；failed/unknown 可重排（attempts+1），超限转人工；**done 不可回退**（除人工审计纠错，需 ledger 记录）。

### 5.4 完成判据三层

1. **页面数字**：课程进度 N/59 增加且与任务类型相符；任务点 `jobUnfinishCount` 变化符合预期（视频 2→1、测验 1→0）。
2. **页面标记**：章节卡片/任务点状态（已完成/绿勾/已完成任务点文案）。
3. **证据文件**：截图 + JSON + jsonl 齐全、时间戳连续、可由第三方复算。

> 三源全过才 done；缺一 → unknown。

### 5.5 提交类任务额外闸门

- 默认 `gate=none`（测试模式，只填不交）。
- 生产提交需：confidence ≥0.8、unknown=0、覆盖 100%、人工确认、提交前落盘（题目+显示字母+提交码+截图+复核）。
- 提交后必须对账（结果页/进度/任务点/第 N 次作答），并写 ledger；**失败不重试提交**。
- 1.1 实测：提交链路成功（100/100，第 1 次作答），见 `docs/规划-本地模型答题-2026-11-07.md §4.7`。

## 7. 端到端流程时序（学习通示例）

~~~
T0 感知：CDP 截图课程/章节页 → VLM 识别 → perception.json
        识别出：28 个章节测验（1.1 已完成）、23 个视频、3 个非视频（excluded）、进度 6/59
T1 规划：主模型生成 tasks.json（28 测验 + 23 视频，其中 1.1 done；27 测验 pending；deps 待 M4 实测）
T2 调度：取 ready（如 quiz-1.2）→ 生成自包含任务书 → 派 fresh 子 agent
T3 执行：子 agent 打开 1.2 测验 iframe → 截图 → VLM 作答（≈2.6 min）→ DOM 回填 → 复核
T4 回执：{task_id, status, key_numbers, evidence[], errors[], submitted:false}
T5 校验：三源对账（进度/任务点/截图）→ 通过 → board 标记 done；写 ledger
T6 循环：下一个 ready → ...；主上下文只看 board 摘要
T7 汇总：剩余任务/完成率/准确率/异常；人工确认后决定是否进入提交（逐节授权）
~~~

## 9. 风险与缓解
